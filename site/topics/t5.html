  1. 01

    设计一个 LLM-as-judge 评估。它有哪些已知偏差？如何校正？

    Perplexity字节跳动滴滴1 条原文答案
    本站答题要点 + 原文答案

    LLM-as-judge 是用强模型按评分标准给输出打分或做 pairwise 比较。已知偏差：位置偏置、长度偏置、自我偏好（偏好同族模型）、格式/谄媚偏置、以及标准模糊导致的方差。校正靠交换位置、长度归一、多评委集成、给出细粒度 rubric 与参考答案、并用人工标注校准。

    • pairwise 比 absolute 打分更稳；必须随机交换 A/B 位置并统计一致性。
    • rubric 要可观察（“是否引用了给定文档”），避免“回答得好不好”这种主观维度。
    • 用 Cohen's kappa / 与人工的一致率验证评委，而不是假设它可信。
    • 成本：评委调用也是 token，离线评估要缓存；在线只能抽样。

    原文答案：LLM 作为裁判(LLM as a Judge)

  2. 02

    当没有标注真值、专家又很贵时，如何构建评估集？

    CohereHarvey
    本站答题要点 + 原文答案

    没有真值时，用“专家产出 + 众包 + 模型辅助”组合：先让领域专家写 50–200 条高质量种子，再用强模型基于文档生成候选并由专家审核；对主观题用多人评分取一致性；同时保留一组“无法回答”的负样本。关键是覆盖真实流量分布，而不是随机抽样。

    • 从线上日志分层抽样（按意图、语言、长度），保证评估集代表真实使用。
    • 模型生成标注要有人工抽检与仲裁，记录标注指南与分歧。
    • 主动学习：优先标注模型不确定或评委分歧大的样本。
    • 评估集要版本化、隔离，避免被训练数据污染。
  3. 03

    在生产 RAG 系统中，如何检测和度量幻觉？

    AnthropicOpenAICursor字节跳动滴滴美团
    本站答题要点 + 原文答案

    幻觉检测分三层：检索层看证据是否存在且被正确引用；生成层用 NLI/LLM 逐句判断“是否被上下文蕴含”；产品层看用户反馈与人工抽检。指标用忠实度（faithfulness）、引用准确率、无支撑主张率，并对高风险领域单独设阈值。

    • 先区分“与上下文矛盾”和“上下文没提但事实正确”，两者处理方式不同。
    • 自动指标用 RAGAS 类的 faithfulness/answer relevance，但要抽样人工校准。
    • 线上：引用点击率、用户纠错、重复追问都是弱信号，可聚合告警。
    • 缓解：强制引用、降低温度、允许“不知道”、检索不足时拒答。
  4. 04

    设计一个回归门禁，用来决定 prompt 或模型改动能否上线。

    Anthropic
    本站答题要点 + 原文答案

    回归门禁 = 固定评估集 + 明确阈值 + 自动跑批 + 人工复核。每次 prompt/模型/检索改动跑同一套离线评估（任务准确率、忠实度、安全、延迟、成本），任何一项跌破阈值就阻断；再做小流量灰度，对比在线指标后才全量。

    • 评估集要覆盖：核心任务、边界/对抗样本、历史事故回归用例。
    • 阈值按业务定，并区分“必须不降”和“允许波动”；用置信区间而不是单点。
    • 把评估跑进 CI，输出 diff 报告（哪条变好/变坏），而不是一个总分。
    • 灰度阶段看真实指标：任务成功率、追问率、投诉率、p95 延迟。
  5. 05

    为什么基准分数提升了，用户却说系统变差了？请列举原因。

    Cognition
    本站答题要点 + 原文答案

    基准涨而用户说变差，常见原因：基准不代表性（污染/过易/分布偏移）、优化了错误目标（长度、格式分）、真实流量里的长尾/多语言退化、延迟或成本上升、以及交互层改动（引用消失、语气变化）。基准测的是能力，用户感受的是任务完成率与体验。

    • 先看分群指标：新模型可能在某类 query 上大涨、另一类上暴跌，平均分掩盖了问题。
    • 检查非质量因素：TTFT 变慢、流式卡顿、格式变化导致前端解析失败。
    • 用户的主观“变差”常来自风格变化（更啰嗦/更冷淡）而非正确率。
    • 补救：把线上失败样本回流进评估集，建立“用户感知指标”与离线指标的映射。
  6. 06

    什么是基准污染(benchmark contamination)？如何防范？

    Zhipu AIAlibabaScale AI1 条原文答案
    本站答题要点 + 原文答案

    基准污染是评测题目（或近似改写）出现在训练数据里，导致分数虚高。防范：训练数据去重与 n-gram 重叠检测、用私有/holdout 集与动态生成的题目、时间切分（训练截止后发布的题）、以及 canary 字符串检测。

    • 常见形式：题目原文、答案、以及中文翻译版进入预训练语料。
    • 检测：13-gram 重叠、嵌入相似度、以及对模型做“背题”探测（给题目前半句看能否补全）。
    • 报告分数时要说明污染检查结果，尤其是公开榜单。
    • 自建评估集要保持私密，避免被下一代模型训练吸收。

  7. 07

    生产级 LLM 系统需要哪些可观测性：traces、spans、成本、反馈？

    1 条原文答案
    本站答题要点 + 原文答案

    生产可观测性要覆盖：请求级 trace（每一步的 prompt、检索片段、工具调用、token 数、耗时、成本）、会话级上下文、质量信号（用户反馈、引用点击、重试）、以及系统指标（QPS、错误率、GPU 利用率、缓存命中）。核心是能把“一次坏回答”完整回放。

    • trace/span 模型：gateway → retrieval → rerank → LLM → postprocess，每段独立计时与计费。
    • 采样：全量存元数据，正文按比例采样或脱敏后存储。
    • 成本要按租户/功能拆分，否则无法定位“谁在烧钱”。
    • 告警：错误率、p99、无答案率、judge 分数下滑、缓存命中骤降。

  8. 08

    在生产中如何管理 prompt 版本和回滚？

    本站答题要点 + 原文答案

    Prompt 要像代码一样管理：存在版本库、有 diff、有评审、有语义化版本号；运行时按 experiment/租户固定版本；回滚是一键切回上一版本并清理缓存。配套要有 prompt 注册表、模板变量校验和 A/B 分流。

    • 禁止线上直接改字符串：必须走发布流程，否则无法复现。
    • prompt 变更要让前缀缓存失效，发布时要预期 TTFT 短时上升。
    • 模板变量做 schema 校验，缺字段直接失败而不是渲染出 undefined。
    • 记录 prompt_version 到 trace，才能把质量变化归因到具体版本。
  9. 09

    设计在线评估：你会记录什么、采样什么、对什么做 A/B？

    Perplexity
    本站答题要点 + 原文答案

    在线评估记录：每次请求的输入、检索结果、输出、引用、延迟、token 成本、用户反馈（点赞/点踩/改写/追问）；按流量分层采样做人工或 LLM 评审；A/B 以会话为单位分流，主指标是任务成功率，护栏指标是延迟、成本、安全违规率。

    • 分流要按用户/会话哈希，避免同一用户在两版之间跳变。
    • 主指标要贴近业务（解决率、转化、留存），而不是 token 相似度。
    • 护栏指标先定，避免为了效果牺牲延迟/安全。
    • 实验周期要覆盖周内波动，样本量先算功效。
  10. 10

    如何评估一个 agent(相对于单次模型回答)？

    Moonshot AIZhipu AIScale AICognition阿里巴巴(淘天、阿里云)字节跳动美团1 条原文答案
    本站答题要点 + 原文答案

    Agent 评估要评轨迹而不只是最终答案：任务成功率、步骤数/成本、工具选择正确率、参数正确率、错误恢复能力、以及是否越权/产生副作用。用可执行环境（沙箱、模拟 API）跑端到端用例，再用 LLM-judge 评过程合理性。

    • 单次回答评估只看文本；agent 要看“做了什么”，所以必须有环境状态断言。
    • 用例要包含：正常路径、工具失败、需要澄清、需要拒绝、长尾多跳。
    • 指标：pass@k（多次尝试成功率）、平均步数、无效调用率、人工介入率。
    • 回归集要冻结环境版本，否则工具行为变化会让结果不可比。
